## 3. Architecture Analysis

### Architectural Style
**Modular Monolith** — single deployable binary that embeds both the compiled frontend (Go `embed`) and all backend services. Clean separation into layers with clear interface boundaries.

### Layer Organization

```
HTTP Layer        server/           chi router, middlewares, auth guards, rate limiting
API Layer         server/subsonic/  Subsonic/OpenSubsonic REST handlers
                  server/nativeapi/ Native JSON-server REST (react-admin)
                  server/public/    Public share routes
Core Layer        core/             Business logic (streaming, artwork, playlists, etc.)
Domain Layer      model/            Interfaces (DataStore, Repository) + domain structs
Persistence Layer persistence/      SQLite implementations of all Repository interfaces
Adapters Layer    adapters/         Third-party HTTP clients (Last.fm, ListenBrainz, Deezer)
Config Layer      conf/             Viper-based config with struct tags + env var override
Scanner           scanner/          4-phase filesystem scanner
Plugins           plugins/          Wasm plugin host + built-in plugin implementations
```

### Dependency Injection
Uses **Google Wire** (compile-time code generation). Injectors are in `cmd/wire_injectors.go`; generated bindings in `cmd/wire_gen.go`.

### Communication Patterns
- **HTTP/REST** — Primary API (Subsonic + Native)
- **Server-Sent Events** (SSE) — `server/events` — real-time UI updates (scan progress, now-playing, refresh)
- **WebSocket** — Plugin callbacks
- **FFmpeg subprocess** — Spawned per transcode/stream request via `core/ffmpeg`
- **MPV IPC socket** — `dexterlb/mpvipc` for Jukebox mode

### External Integrations
| Service | Purpose | Package |
|---|---|---|
| Last.fm | Artist metadata, scrobbling, OAuth | `adapters/lastfm` |
| ListenBrainz | Scrobbling | `adapters/listenbrainz` |
| Deezer | Artist metadata | `adapters/deezer` |
| Unsplash | Login backgrounds | URL-based |
| FFmpeg | Transcoding, probing | `core/ffmpeg` |
| MPV | Jukebox server-side playback | `core/playback` |

## 5. Coding Standards

### Go
- **Naming**: standard Go conventions — PascalCase exports, camelCase private, `_test.go` suffix for tests
- **Errors**: returned as `(result, error)` pairs; `model/errors.go` defines domain error sentinels
- **Interfaces**: defined in `model/` (dependency inversion) — core only depends on `model`, never `persistence`
- **DI**: all wiring via Google Wire; no `init()` side effects for wiring
- **Tests**: Ginkgo v2 BDD suites (Describe/It/BeforeEach); test suites per package with `_suite_test.go`
- **Logging**: structured key-value pairs via `log` package wrappers (`log.Info(ctx, "msg", "key", val)`)
- **Config**: all options in `conf.configOptions` struct; env vars prefixed `ND_` override file config
- **Build tags**: `netgo,sqlite_fts5` required for all production builds
- **Linting**: golangci-lint v2 with gosec, errorlint, gocyclo, gocritic enabled

### JavaScript/React
- **Style**: Prettier (enforced in CI) + ESLint v8
- **Components**: functional components with React hooks; PropTypes for prop validation
- **State management**: Redux with redux-saga for async side effects; react-admin resource model
- **Naming**: PascalCase components, camelCase functions/variables, kebab-case CSS
- **Testing**: Vitest + @testing-library/react; component tests co-located (`*.test.jsx`)
- **i18n**: all user-facing strings via `useTranslate()` hook (ra-i18n-polyglot)

### API
- **Subsonic**: Versioned at `1.16.1`; supports both XML and JSON responses (content negotiation)
- **Native API**: RESTful, react-admin JSON-server protocol, versioned at `/api/{resource}`
- **Auth**: JWT in `X-ND-Authorization` header or `jwt` cookie; Subsonic uses `u`/`p`/`t`/`s` query params
- **Error format**: Subsonic error envelopes; Native API uses standard HTTP status codes

## 8. Security Analysis

### Authentication
- JWT HS256 with a randomly-generated secret stored encrypted in the `properties` table
- Secret encrypted with AES-GCM using a configurable `PasswordEncryptionKey`
- Default fallback key exists (`consts.DefaultEncryptionKey`) — **must be overridden in production**
- Session timeout: 48 hours default (configurable)
- Subsonic: MD5 token or plain-text password (plain-text is deprecated by spec)

### Authorization
- Per-request: `server.Authenticator` middleware injects user into context; `server.AdminRequired` guard on admin routes
- Library access: `user.HasLibraryAccess(libraryID)` checked per data access
- Plugin permissions: explicit allow-list per plugin (users + libraries + write access flag)

### Input Validation
- `unrolled/secure` middleware sets `X-Frame-Options`, `X-Content-Type-Options`, `X-XSS-Protection`, HSTS
- `go-chi/cors` with configurable origins
- `microcosm-cc/bluemonday` HTML sanitizer used for user-provided content (e.g., playlist comments)
- Subsonic params validated via `utils/req` helpers
- `santhosh-tekuri/jsonschema v6` for JSON plugin config validation

### Secrets Management
- JWT secret: encrypted in DB, key from config
- User passwords: stored encrypted (AES), not bcrypt — **potential concern** for password-at-rest security
- LastFM/ListenBrainz tokens: stored in `user_props` table

### Known Security Concerns
- Password storage uses AES encryption (reversible) rather than a hashing algorithm (bcrypt/argon2). This is intentional for Subsonic MD5 challenge support but represents a trade-off.
- `DefaultEncryptionKey` is hardcoded and public — installations that don't set `PasswordEncryptionKey` use a known key.
- Rate limiting only on `/auth/login`; Subsonic auth endpoints are not rate-limited.

## Missing Documentation

- No OpenAPI/Swagger spec for the Native REST API (`/api/*`)
- No CHANGELOG or structured release notes
- Plugin development guide exists (`plugins/README.md`) but host service API is undocumented at the interface level

## Technical Debt

- **React 17 + react-admin v3**: Both are significantly outdated (React 19, react-admin v5 are current). Migration would be a large effort.
- **Material-UI v4**: Superseded by MUI v5/v6; migration to `@mui/material` is pending.
- **Wire generated code**: `cmd/wire_gen.go` is a large generated file checked into git — requires discipline to keep in sync.
- **JSX instead of TSX**: Frontend uses `.jsx` (JavaScript) not `.tsx` (TypeScript) despite TypeScript devDependencies being present.
- **Password encryption vs hashing**: AES-reversible encryption for passwords (required by Subsonic MD5 challenge) is a known limitation.
- **Subsonic API versioning**: Pinned at `1.16.1`; OpenSubsonic extensions partially implemented.

## Architectural Risks

- **SQLite concurrency**: WAL mode mitigates but does not eliminate write contention under heavy parallel scan + stream load.
- **CGO dependency**: mattn/go-sqlite3 requires CGO — complicates build toolchains and cross-compilation.
- **FFmpeg as external binary**: Feature availability (transcoding, probing) is environment-dependent; no graceful degradation path documented.
- **Embedded frontend**: Changing the frontend requires a full Go rebuild. Dev mode decouples this, but CI must always build UI first.
- **Plugin sandbox security**: Wasm sandboxing via wazero is generally safe, but the `allowWriteAccess` flag on plugins grants filesystem write permissions — needs careful review per plugin.

## Security Concerns (Requires Manual Review)

- `consts.DefaultEncryptionKey` is public and hardcoded — all deployments not setting `PasswordEncryptionKey` share the same key.
- Subsonic plain-text password authentication path (`p=` parameter) is still supported — should be disabled or warned against.
- Share links use JWT with configurable expiry; ensure `DefaultShareExpiration` is appropriate for production.
- Rate limiting only covers `/auth/login`; Subsonic authentication (`/rest/ping` with credentials) is unrestricted.
